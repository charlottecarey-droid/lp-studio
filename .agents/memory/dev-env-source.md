---
name: Dev env source in this Repl
description: Where dev-workflow processes actually read env vars from in this monorepo.
---

Dev workflows in this Repl read env from THREE sources: `.replit`'s `[userenv.shared]` block, gitignored `.env` files (loaded via `dotenv` / `--env-file-if-exists`), AND Replit Secrets (Tools → Secrets) — Secrets ARE injected into dev workflow shells.

**Why:** Confirmed empirically May 31 2026 — `GITHUB_OAUTH_CLIENT_ID`/`GITHUB_OAUTH_CLIENT_SECRET` (and `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`) were set ONLY as Replit Secrets, absent from `.env`, yet the dev api-server read them (`/api/auth/github/config` → `enabled:true`, redirect carried the real client_id). An EARLIER May-2026 observation claimed the opposite (`CSRF_SECRET` only worked once added to `.env`) — that is now stale; treat platform Secret-injection into dev workflows as the current truth and verify empirically if in doubt.

**How to apply:** A dev secret can live in EITHER gitignored `.env` (project root) OR Replit Secrets — both reach the dev workflow. Prefer Replit Secrets (via the environment-secrets requestEnvVar flow) for credentials so they aren't sitting in a file. NEVER put a secret in `.replit`'s `[userenv]` — it is committed to git.

**`.env` does NOT beat an injected Secret unless you force override.** Node's native `--env-file` / `--env-file-if-exists` (and plain `dotenv.config()`) will NOT overwrite an env var that is already set in the process — so an injected Replit Secret WINS over `.env`. Confirmed empirically June 10 2026: a stale prod `NEON_DATABASE_URL` Secret kept winning over a staging value in `.env` across workflow restarts. To make `.env` authoritative over an injected Secret you must load it with `dotenv` `{ override: true }` as the FIRST import of every entrypoint (here: a shared `loadEnv.ts` imported first in `instrument.ts` AND `migrate.ts`, so the override runs before `@workspace/db` builds its pool). Verify the flip by setting a sentinel value in the shell and confirming the post-override host. To hard-disable a service whose Secret you can't unset (e.g. point R2 off the prod bucket), set the key to empty in `.env` (override blanks it → `getR2Config()` returns null).

**Sensitive credentials → use global Replit Secrets, NOT `[userenv.production]`/`[userenv.shared]`.** Those `[userenv]` blocks are written as PLAINTEXT into the git-tracked `.replit`, so any value there leaks to source control. Global Secrets inject into BOTH the prod deployment runtime AND dev workflows (confirmed: `STRIPE_SECRET_KEY` Secret → dev log shows `[stripe] enabled via STRIPE_SECRET_KEY env var (portable mode)`; `STRIPE_ENABLED` present in prod runtime). Corollary: you can NOT rely on "Secrets don't reach dev" to keep dev on a fallback path — if dev must differ from prod, gate it in code (e.g. on `NODE_ENV`) or omit the Secret and use `.env`/`[userenv]` only where intended. Non-sensitive prod config (e.g. `PUBLIC_API_BASE_URL`) is fine as a plaintext `[userenv.production]` env var.
