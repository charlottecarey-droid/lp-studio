Step 1 — Schema additions: scope + tenant_id
Add two columns to notification_templates:
sqlALTER TABLE notification_templates
  ADD COLUMN scope TEXT NOT NULL DEFAULT 'platform'
    CHECK (scope IN ('platform', 'tenant')),
  ADD COLUMN tenant_id INTEGER REFERENCES tenants(id) ON DELETE CASCADE;

-- Platform-scope rows have tenant_id NULL. Tenant-scope rows MUST have tenant_id set.
ALTER TABLE notification_templates
  ADD CONSTRAINT notification_templates_scope_tenant_check
  CHECK (
    (scope = 'platform' AND tenant_id IS NULL) OR
    (scope = 'tenant' AND tenant_id IS NOT NULL)
  );

-- Key uniqueness changes — was unique on (key) alone, now unique on (scope, tenant_id, key):
--   - Platform-scope: (scope='platform', tenant_id=NULL, key='welcome') unique
--   - Tenant-scope:   (scope='tenant', tenant_id=42, key='lead_notification') unique
DROP INDEX IF EXISTS notification_templates_pkey;
ALTER TABLE notification_templates DROP CONSTRAINT IF EXISTS notification_templates_pkey;
ALTER TABLE notification_templates ADD PRIMARY KEY (scope, tenant_id, key);
-- (Or: keep `id` as PK and add UNIQUE(scope, tenant_id, key) — whichever matches existing convention. Check the migration journal for the current PK shape.)
Existing Phase 1 rows all get scope='platform' automatically via the DEFAULT. No data migration needed beyond the ALTER.
Add a tenant master shell table — separate from notification_templates because the shell is per-tenant and stored as a single row per tenant:
sqlCREATE TABLE IF NOT EXISTS tenant_email_shells (
  tenant_id INTEGER PRIMARY KEY REFERENCES tenants(id) ON DELETE CASCADE,
  shell_html TEXT NOT NULL,
  logo_url TEXT,
  header_bg_color TEXT NOT NULL DEFAULT '#F6F2E9',
  header_text_color TEXT NOT NULL DEFAULT '#1A1815',
  footer_html TEXT NOT NULL DEFAULT '',
  reply_to_email TEXT,
  physical_address TEXT,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_by INTEGER REFERENCES app_users(id)
);
Each tenant has ONE shell. If the row doesn't exist (tenant hasn't configured it), the renderer falls back to a default tenant shell derived from the tenant's existing brand config (logo, primary color, etc.) — which is the right zero-config experience.

Step 3 — Resolver: scope-aware template lookup
Extend dispatchNotification to accept a scope + optional tenantId parameter, OR create a wrapper dispatchTenantNotification that calls into the same core path with scope='tenant'.
Resolution order for a tenant-scope send:

DB lookup: notification_templates WHERE scope='tenant' AND tenant_id=$1 AND key=$2 AND enabled=true
If missing OR disabled: code default from TENANT_EMAIL_TEMPLATES[key]
If code default missing: log loudly, throw (this should never happen in production — every tenant template MUST have a code default per the contract above)

Resolution order for the SHELL:

DB lookup: tenant_email_shells WHERE tenant_id=$1
If missing: derive a default tenant shell from lp_brand_settings.config (logo, primary color, etc.)
If brand config missing: fall back to LP Studio's platform shell from emailRender.ts

The render path becomes:
tsexport async function renderTenantEmail(
  tenantId: number,
  key: string,
  vars: Record<string, unknown>
): Promise<{ subject: string; html: string; text: string }> {
  const tpl = await getTenantTemplate(tenantId, key);          // DB override or code default
  const shell = await getTenantShell(tenantId);                // DB override or brand-derived or platform fallback
  const expanded = expandTenantEmailVars(vars, tenantId);       // tenant variable registry
  const html = renderInShell(shell, tpl.emailBody, expanded);
  const text = interpolatePlainText(tpl.emailBody, expanded);
  const subject = interpolateString(tpl.emailSubject, expanded);
  return { subject, html, text };
}
Same shape as renderSystemEmail from Phase 1, just scoped to tenant.

Why this is the right scope
1. Reuse the Phase 1 components — don't fork. The EmailWYSIWYGEditor, the dispatchNotification, the render pipeline, the SuperAdmin editor surface — all designed to be scope-aware. Phase 2 adds a scope column and a tenant-side UI route; everything else extends. This is the cheap version of the work.
2. Brand-derived defaults so zero-config tenants look right immediately. Most tenants won't configure their email shell explicitly — they'll just expect their lead notifications to look like their brand. By deriving the default shell from lp_brand_settings.config (logo, primary color, etc.) at render time, tenants get correct-looking emails without ever touching the shell editor. Configuration is for tenants who want to override the defaults, not for the basic case.
3. The lead notification email is the highest-leverage migration. Every non-Dandy tenant currently sends Dandy-branded lead notifications when a form is submitted on their landing page. That's the visible Dandy-leak issue we've been chasing across the one-pager + microsite work, now showing up in transactional emails. Phase 2 fixing this single email arguably matters more than building the editor — the editor is the long-term capability, but the migration is the immediate cleanup.
What this prompt explicitly doesn't do

Doesn't replace the existing sales campaign system — campaigns are tenant-authored outbound to prospects, already editable, separate concern.
Doesn't add new template-type creation from UI. Tenants edit what's seeded; they can't author entirely new templates. Phase 3 lifts this.
Doesn't add new triggers from UI. Triggers are wired in code; tenants can disable templates but not create new triggers.
Doesn't add multi-step workflows. That's Phase 3 — extends the campaign scheduler pattern.
Doesn't change how notification_sends (the in-app inbox + send log) is structured. Same table, same dispatcher pipeline.
Doesn't bring tenant emails into the welcome-issue magazine style. Tenant emails should look like THE TENANT, not like LP Studio. The magazine framing stays scoped to LP Studio's onboarding emails.
