I have an existing multi-tenant landing page app deployed on Replit/GCP, with a Cloudflare edge layer in front (R2-prerendered HTML, worker-based routing, Custom Hostnames via Cloudflare API). New tenants onboard themselves through my app UI: they enter a hostname, my app provisions a Cloudflare Custom Hostname via API, and they add a single CNAME to their DNS pointing at <hostname>.cdn.cloudflare.net. Cert issuance happens automatically via CNAME-based DCV. This works great for greenfield hostnames.
The problem: this flow doesn't work for tenants who already have a live A record serving real traffic on the hostname they want to migrate. If they just flip the CNAME, there's a TLS gap between when Cloudflare starts receiving requests and when the cert is issued — visitors see SSL errors during that window. For live-traffic migrations, the workaround is to pre-provision the cert via explicit TXT + CAA records (_cf-custom-hostname.*, _acme-challenge.*, CAA issue "ssl.com") so the cert is ready before any DNS change. I just did this manually for a tenant (Dandy) using a staged runbook: add 6 records → wait for cert → flip partners hostname → monitor 24–48h → flip lp hostname → monitor. The runbook works but it's manual, slow, and error-prone.
Important context I learned while doing the Dandy migration: HSTS is the dominant constraint here, not just paid-traffic-vs-organic. Dandy has strict-transport-security: max-age=31536000; includeSubDomains set on the apex, which means any TLS gap during cutover would hard-fail for any user who's visited any meetdandy.com page in the last year — no "proceed anyway" escape hatch in the browser. I expect this to be the norm, not the exception, for enterprise tenants. So the automation I want is specifically for the zero-gap pre-validation path; the "accept a short gap" path isn't a safe default for live-traffic migrations against HSTS-protected zones, and I don't want to offer it as an easy choice in the UI.
