/** True when the given layout-defaults key is for a Dandy-gated built-in
 *  template (e.g. `dandy_comparison_template_layout`,
 *  `dandy_agreement_summary_template_layout`). Used by the api-server to
 *  reject PUTs from non-Dandy tenants. */
export function isDandyGatedLayoutKey(key: string): boolean {
  if (!key.startsWith("dandy_")) return false;
  if (!key.endsWith("_template_layout")) return false;
  const builtinId = key.slice("dandy_".length, -"_template_layout".length).replace(/_/g, "-");
  return isDandyGatedBuiltin(builtinId);
}

Why this is the right scope
1. Fix pdf.ts properly, not with band-aids. The simplest fix would be to swap dandyLogoWhiteUrl for tenantLogoUrl at the two call sites and call it done — but that leaves the QR fallback and the text-fallback leaks. Doing the signature change once, surfacing brandOpts as a single object, makes future hardening (e.g. CSS color, default font) one-place changes instead of N call-site changes.
2. Server-side defense in depth on layout-defaults. The client filter is sufficient for trustworthy admins but not for a real boundary. The server gate adds zero cost for legitimate Dandy admins (single fast slug check) and closes a class of "non-Dandy admin curl'd the API directly" attacks. The pattern matches every other Dandy-gated route already shipped (one-pager-templates.ts, web-one-pager.ts).
3. Switch the editor's isDandy source as part of this work, not later. The brand.brandName === "dandy" pattern survives in the editor because it predates the brand.isDandy flag. Leaving it inconsistent invites a future engineer to copy the wrong pattern into a new file.
