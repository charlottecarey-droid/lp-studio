Replit Prompt — SEO Robots Controls (Tenant + Page Level)
Add two boolean controls per scope (tenant-default + page-override) that drive a <meta name="robots"> tag on published pages:

Allow search engines and LLMs to index this page — when off, emits noindex
Let search engines follow links on this page — when off, emits nofollow

Mirror Mutiny's UX pattern: each page-level checkbox shows "Using company default" when the page hasn't overridden the tenant-level setting. Three-state per page: null = inherit tenant, true = force allow, false = force deny.
This is a companion to the custom-html-injection prompt (replit-prompt-custom-html-injection.md) — both features add to the same prerender pipeline and share UI infrastructure (settings page nav, page properties panel). They're scoped as separate prompts because:

Robots controls are simple meta tags, no security implications, free for all tiers
Custom HTML is raw script injection, admin-only, plan-gated

Ship together or sequentially — no blocking dependency between them.

Why this matters for LP Studio specifically
ABM is the primary use case. Account-personalized microsites (e.g. "Zoom for Salesforce") generally should NOT be indexed by Google — they're 1:1 personalized pages, not public marketing. Today LP Studio has no way to set this — every published page is implicitly index/follow, which means tenant microsites can accidentally surface in search results for prospect company names. Embarrassing at best, leaks at worst.
The fix is small and table-stakes for any landing-page tool. Webflow, Unbounce, Mutiny, Framer all have it.

Step 1 — Schema additions
lp_pages table — add two NULLABLE boolean columns. NULL means "inherit tenant default":
sqlallow_indexing  BOOLEAN,  -- NULL = inherit, true = index, false = noindex
allow_following BOOLEAN   -- NULL = inherit, true = follow, false = nofollow
NULLABLE is intentional — it's the three-state semantics the UI needs ("Using company default" when null). Don't add defaults at the DB level; the application resolves NULL → tenant default at render time.
Tenant config — add two NON-NULL boolean fields under whichever JSONB shape matches existing convention. Recommend nesting under a seo key:
ts// BrandConfig (or wherever tenant config lives)
seo?: {
  allowIndexing: boolean;   // tenant default
  allowFollowing: boolean;  // tenant default
};
Important: dual-default pattern. The defaults differ for migration vs. new-tenant creation:

Migration of existing tenants: default both to true. No behavior change — existing tenants' pages keep being indexable exactly as they are today. Their current behavior is "no robots meta tag → implicit index+follow"; the new fields set to true preserve that exactly.
New tenants going forward: default both to false (noindex, nofollow). LP Studio is primarily an ABM tool; the typical first page a new tenant publishes is an account-personalized microsite (e.g. "Zoom for Salesforce") and those should not appear in public search results for the prospect's brand name. Safer-by-default. Admins flip indexing on for evergreen pages or for tenant-wide indexing.

Find the tenant-creation code path (probably in artifacts/api-server/src/routes/admin.ts or wherever new tenants are provisioned — grep for tenant INSERT or db.insert(tenantsTable)) and seed seo: { allowIndexing: false, allowFollowing: false } into the new tenant's brand config at creation. For the migration on existing tenants, write true/true into every row.
Document the dual-default loudly in code comments next to both code paths so a future engineer doesn't "fix" the inconsistency by aligning them.

Step 2 — Resolution helper
Add a single helper to compute the effective robots state:
ts// In a shared lib (e.g. lib/seo/robots.ts or alongside injectPageMeta.ts)
export function resolveRobotsMeta(opts: {
  pageAllowIndexing: boolean | null;
  pageAllowFollowing: boolean | null;
  tenantAllowIndexing: boolean;
  tenantAllowFollowing: boolean;
}): { indexing: boolean; following: boolean } {
  return {
    indexing: opts.pageAllowIndexing ?? opts.tenantAllowIndexing,
    following: opts.pageAllowFollowing ?? opts.tenantAllowFollowing,
  };
}

/** Produces a robots meta-tag content string, or null if no tag is needed
 *  (i.e. both indexing and following are true — the implicit default).
 *  Returns "noindex", "nofollow", or "noindex,nofollow" when an override
 *  is needed. Never emits "index" or "follow" — those are implicit. */
export function robotsMetaContent(state: { indexing: boolean; following: boolean }): string | null {
  const parts: string[] = [];
  if (!state.indexing)  parts.push("noindex");
  if (!state.following) parts.push("nofollow");
  return parts.length ? parts.join(",") : null;
}
Pure functions, easy to unit test, no I/O. Reused by both the prerender path and the live SPA usePageMeta hook.

Why this is the right scope
1. Three-state nullable column for page-level, not boolean. A nullable column is the simplest way to model "use tenant default unless explicitly overridden." A boolean with a separate _isOverridden flag is more brittle and harder to migrate. NULL semantics let the resolution helper stay one line (?? tenantDefault).
2. No meta tag when default. Don't emit <meta name="robots" content="index,follow"> — that's the implicit default and adding a redundant tag clutters the HTML. Only emit the tag when at least one override is needed. Cleaner output, smaller bytes, no SEO downside.
3. No plan gating. Robots controls are table-stakes SEO. Every CMS has them free. Gating them behind a paid tier looks petty and would surprise customers who expect basic SEO controls in any landing-page tool. The cost to LP Studio is zero (small boolean fields, tiny meta tag injection); gate something else.
What this prompt explicitly doesn't do

No JSON-LD structured data. Mutiny includes a JSON-LD editor + AI-regenerate-on-publish feature in the same UI panel. For LP Studio v1, this is over-scoped — ABM microsites are noindex'd anyway, so JSON-LD provides no value for the primary use case. For evergreen marketing pages it has real SEO upside, but it's not table-stakes. Add when a customer asks. The Mutiny AI-generation feature is a nice differentiator but it's a meaningful project on its own (page-intent inference, schema selection, content extraction).
No microsite robots controls. Same scope boundary as custom-html-injection.
No per-page sitemap exclusion controls. Implicit — noindex pages get filtered from the sitemap automatically. If admins want page-level sitemap visibility separate from indexing, that's a v1.1 follow-up.
No <meta name="googlebot"> or <meta name="bingbot"> per-crawler controls. Generic name="robots" covers every major crawler. Per-crawler overrides are advanced SEO and not requested.
No noarchive, nosnippet, max-snippet, noimageindex controls. Future feature if anyone asks. The two checkboxes Mutiny exposes cover 99% of the use case.
