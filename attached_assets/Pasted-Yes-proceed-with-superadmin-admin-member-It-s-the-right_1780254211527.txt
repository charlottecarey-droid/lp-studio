Yes, proceed with superadmin / admin / member. It's the right v1 model for three reasons:

It's what the data model actually supports. tenant_roles is dynamic per-tenant with free-text names + an isAdmin boolean, so a fixed cross-tenant owner/admin/editor/viewer enum doesn't exist. The coarse 3-bucket split (superadmin via app_users.tenantId IS NULL, admin via tenant_roles.isAdmin = true, member for everyone else in tenant_members) is the cleanest map onto reality. My prompt's enum was wrong; the agent's reconciliation is right.
Most audience-filter use cases want exactly these three buckets. "Send to all admins to coordinate a feature rollout" doesn't care whether they're called "owner" or "editor" — just that they have admin access. The isAdmin flag is the structural distinction that matters.
A finer split would require either (a) flattening tenant_roles.name into a fixed enum across all tenants — which breaks per-tenant role flexibility — or (b) letting operators pick free-text role names in the audience filter UI — which is confusing for cross-tenant filtering (Tenant A's "Editor" role isn't the same as Tenant B's "Editor" role). Neither is right for v1.

If a use case ever emerges that needs "send to everyone with role name X across tenants," that's a role_names?: string[] additive filter dimension later. Not now.
