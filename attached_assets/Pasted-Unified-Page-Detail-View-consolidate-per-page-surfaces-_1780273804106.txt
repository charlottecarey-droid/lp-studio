Unified Page Detail View — consolidate per-page surfaces into one route
What we're building
A single Page Detail route that aggregates everything about one landing page in one place — analytics, conversion scoring, page speed, traffic sources, A/B tests, programmatic variables, heatmap, and a per-visit table — instead of scattering those across six different Labs/Analytics tabs.
Today the IA is feature-centric: Conversion Scoring is its own tab in Labs, Page Speed is its own tab in Labs, AdMap is its own tab in Labs, the per-page metrics live in the builder sidebar, A/B Tests are their own tab, Approvals are their own tab. To understand how one page is performing, an operator has to traverse 5–7 surfaces. That's the problem.
The fix is entity-centric IA: one route per page at /analytics/pages/[pageId] that consolidates all per-page data into a single operating dashboard. Think CRM contact-detail page, but for a landing page.
Important: don't remove the existing Labs tabs. Those remain useful as cross-page rollups (e.g. "which of my 143 pages are failing on Conversion Score?"). They become the inventory view. The new Page Detail view is the per-entity drill-down. Both are needed.
Scope: this is mostly a UI consolidation, not a data engineering build
The data already exists. Almost every component on this page already has a working implementation somewhere in the codebase — in the builder sidebar, in Labs/Conversion Scoring, in Labs/Page Speed, etc. The work is:

Extract those existing implementations into reusable shared components.
Build one new route that composes them.
Build one net-new component: the Visits Table (the per-visit drill-down with resolved contact identity).
Wire navigation so users can land here from Analytics > Pages, from Labs/*, and from the Builder.

Time estimate: 3–5 focused days if data is where I expect it. Longer if the per-feature data isn't already callable from the per-page level.
Route + file structure
New route: /analytics/pages/[pageId] in the Marketing Console.
Component file: apps/web/src/routes/marketing/analytics/pages/[pageId]/page.tsx (or whatever the existing convention is — match what /analytics/pages uses today).
Why under /analytics/pages/ and not under /pages/: the user mental model is "I'm looking at analytics for a page," and the existing Analytics > Pages table is the natural entry point. The /pages/ route is the editing context (list of pages → click to edit in builder); /analytics/pages/ is the measurement context (list of pages → click to see how it's performing).

Contact name search
"Has converted" toggle (filters to visits with form_submitted = true)

Row click: expand inline to show per-visit detail

Full scroll path (scroll depth over time)
Click sequence (which elements in order)
Time on page (engaged time)
Referrer

The structural advantage to make legible in this table: identity resolution is deterministic because the contact ID comes from the URL token at send time, not from third-party cookie matching. That means rows show resolved contacts even for cold-outbound visitors who aren't in the user's CRM. This is the wedge against Mutiny's probabilistic identity resolution. Don't make the table look apologetic about anonymous visits — frame them as a separate stream (organic + direct) while making the tokenized visits the hero data.

Components to extract into shared
These currently live inside per-feature routes. They need to be lifted into a shared components/analytics/ directory (or wherever the existing shared analytics components live):

PerformanceScoreCard — currently in /labs/conversion-scoring
PageSpeedCard — currently in /labs/page-speed (the right-side detail panel)
Heatmap — currently in builder sidebar
TrafficSourceBreakdown — currently in /labs/ad-map
ProgrammaticVariablesTable — currently in /labs/programmatic

Each should accept a pageId prop and self-fetch its own data, so the Page Detail view can compose them without a single mega-query.
Why self-fetching components vs one aggregated endpoint: simpler, each section loads independently (faster perceived performance), failures are isolated (Conversion Score failing doesn't blank the whole page), and the existing per-feature endpoints can be reused without modification.
Data layer
Most of the existing per-feature endpoints already accept (or trivially can accept) a pageId filter:

GET /api/analytics/pages/:pageId/summary → the summary strip (likely already exists)
GET /api/conversion-scoring/:pageId → the scoring card
GET /api/page-speed/:pageId → the speed card
GET /api/ad-map?pageId=:pageId → the traffic sources
GET /api/tests?pageId=:pageId → the tests section
GET /api/programmatic/variables?pageId=:pageId → the variables section
GET /api/heatmap/:pageId?type=clicks|scroll&device=*&range=* → the heatmap

The one new endpoint: GET /api/analytics/pages/:pageId/visits?range=*&page=*&limit=50&contactSearch=*&convertedOnly=*&knownOnly=*
Returns a paginated list of visit events with contact identity resolved via the URL token lookup. Implementation:
ts// rough pseudocode — adapt to existing query patterns
SELECT
  pe.timestamp,
  pe.url_token,
  c.id AS contact_id,
  c.name AS contact_name,
  a.id AS account_id,
  a.name AS account_name,
  pe.max_scroll_depth,
  pe.click_count,
  pe.cta_clicked,
  pe.form_submitted,
  pe.location_country,
  pe.location_city,
  pe.referrer,
  pe.utm_source,
  pe.device,
  pe.engaged_seconds
FROM page_events pe
LEFT JOIN contacts c ON c.id = pe.contact_id_from_token
LEFT JOIN accounts a ON a.id = c.account_id
WHERE pe.page_id = $1
  AND pe.timestamp BETWEEN $2 AND $3
  [AND c.name ILIKE '%' || $4 || '%']
  [AND pe.form_submitted = true]
  [AND pe.contact_id_from_token IS NOT NULL]
ORDER BY pe.timestamp DESC
LIMIT 50 OFFSET ($page - 1) * 50;
If the page_events table doesn't already store cta_clicked or max_scroll_depth per visit, that's a slightly bigger lift — check the existing event schema before scoping. The Heatmap already aggregates scroll + click events, so those signals exist somewhere — the question is whether they're stored per-visit or only aggregated. If only aggregated, then the Visits Table either (a) needs schema changes to record per-visit max scroll + cta click, or (b) joins to the raw event stream and computes per-visit on read. Use whichever pattern matches the existing telemetry architecture.
Navigation wiring
Add links into this view from existing surfaces:

/analytics/pages table — clicking a page row navigates to /analytics/pages/[pageId]. (Today the row likely doesn't link anywhere meaningful — make it the primary entry point.)
/labs/conversion-scoring — the per-page dropdown selector remains, but each scored page should have a "View page detail" link.
/labs/page-speed — clicking a page in the list opens this detail view in a new context (in addition to the right-side panel for inline quick-scan).
/labs/ad-map — campaign rows that link to a page should also surface "View page detail."
Builder — add an Open analytics button in the page-settings sidebar header (alongside the existing Performance Score sidebar) that opens /analytics/pages/[pageId] in a new tab.
Direct URL — anyone with the page ID can navigate to /analytics/pages/[pageId] directly.

Performance + loading patterns

Load the header + performance summary strip immediately (these are the fastest queries).
Render each section with its own skeleton/spinner while its data loads, in parallel.
Lazy-load the Heatmap section — it's the heaviest visualization. Load it after the page has settled (or behind an Intersection Observer when the user scrolls near it).
The Visits Table should load 50 rows by default with infinite scroll or pagination — never load all rows up front.

Empty states
Each section needs a non-apologetic empty state:

No conversion analysis: "Run analysis" CTA
No speed analysis: "Run analysis" CTA
No campaigns: yellow callout (specified above)
No tests: explainer + CTA
No variables: explainer + CTA
No visits in date range: "No visits in this period. Try a wider range." with the range selector
Page not published yet: top-level callout "This page is in draft. Publish it to start collecting visit data."

Design constraints

Match existing Marketing Console styling — same typography (DM Sans display, Inter body), same color tokens (cream #F6F2E9, ink #1A1815, indigo #4B47E5, coral #E26B4F, lime #C7E738).
Section dividers should be subtle (1px hairline) — this is a long scroll page; the eye needs anchors but not heavy visual breaks.
Use the same card patterns already in /analytics and /labs/* — don't invent new component styles.
Mobile: collapse the 6-card summary strip into 2 columns × 3 rows. Most other sections can stack naturally.

What NOT to do

Don't remove the existing Labs tabs. They remain valuable as cross-page rollup views.
Don't build a single mega-endpoint that returns everything in one call. Use parallel queries with independent loading.
Don't redesign the existing components. Extract them as-is and compose. Visual polish can come in a follow-up pass.
Don't add new metrics. Use what's already being captured. (Engaged-time-while-tab-is-focused is tempting but skip it — scroll depth + clicks-per-visit covers the same signal more reliably.)
Don't gate this behind a feature flag. It replaces a missing experience, not an existing one. Ship it to all tenants directly.
