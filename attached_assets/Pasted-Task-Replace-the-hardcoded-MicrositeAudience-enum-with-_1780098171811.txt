Task: Replace the hardcoded MicrositeAudience enum with the existing brand-config AudienceSegment[]
Context
The microsite generator (artifacts/api-server/src/routes/sales/generate-microsite.ts) has hardcoded audience branches keyed to Dandy-specific enums (dso-corporate, dso-practice, independent). When the audience matches a Dandy-coded branch, the AI prompt injects Dandy DSO value props ("$1,500 lab credit", "AI Scan Review", "practice efficiency"), Dandy-specific block types (dso-heartland-hero, dso-practice-nav, dso-partnership-perks), and dental vocabulary into the generation regardless of tenant. This produces leaky output for non-Dandy tenants — empirically confirmed by Charlotte generating a Zoom microsite targeting Salesforce with the "Network Leadership" audience and getting "Standardize operations. Protect EBITDA. 200+ practices streamlined. 96% on-time case delivery rate. 5 days average turnaround time" in dental-lab vocabulary.

Brand Settings already exposes a full management UI for it (SegmentCard in artifacts/lp-studio/src/pages/brand-settings.tsx around line 493). And generate-microsite.ts already has findMatchingSegment + buildSegmentSection helpers that consume it (wired today off the per-account segment tag, NOT off the audience picker).
The fix is structural, not additive: stop using the parallel MicrositeAudience enum, and route the audience picker + prompt builder through brand.segments instead. Dandy is configured with segments that match the current hardcoded branches verbatim, so Dandy's behavior is byte-identical pre/post. Zoom uses Zoom's segments. Crunchy uses Crunchy's. Tenants with no segments get a neutral fallback that doesn't mention DSOs.

They help catch some Dandy strings post-hoc, but the empirically-confirmed leakage above shows the structural fix (audience routed through brand.segments) is still needed — the validator catches symptoms, this prompt fixes the source. Step 1 — Make audience-specific block lists configurable per-segment
The hardcoded branches today do two distinct things:

Inject audience copy guidance (which buildSegmentSection(matchedSegment) already does, just driven off the wrong selector).
Specify exactly which block types the AI may emit (this is NOT in AudienceSegment today).

The block list is the only piece we genuinely need to add. Extend AudienceSegment with one new optional field:
tsexport interface AudienceSegment {
  // ...existing fields...

  /**
   * Optional per-segment block-list override for the microsite generator.
   * Each entry is { type, schema } where `type` is a registered block
   * type and `schema` is the prop-shape hint string passed to the AI
   * (same format `BLOCK_PROP_SCHEMAS` uses today). When empty/unset, the
   * generator falls back to the brand's default block list (see below).
   */
  micrositeBlockList?: Array<{ type: string; schemaHint?: string }>;
}
Keep the field optional and additive — existing brand configs without it stay valid. Brand Settings' SegmentCard UI gets one new collapsible section ("Microsite block list — advanced") with an array editor; default it collapsed so non-power-users don't see it.

Step 2 — Add a brand-level default block list with a neutral fallback
Add one more optional field to BrandConfig (not to AudienceSegment):
ts/**
 * Default microsite block list when the selected segment has no
 * `micrositeBlockList` of its own. When this is also unset, the
 * generator uses a built-in neutral set (`hero`, `trust-bar`,
 * `benefits-grid`, `testimonial`, `how-it-works`, `comparison`,
 * `bottom-cta`) — the same one the legacy "independent" branch
 * already used, which doesn't mention DSOs or dentistry.
 */
defaultMicrositeBlockList?: Array<{ type: string; schemaHint?: string }>;
Brand Settings exposes this under the existing "Sales Console" or "Microsite defaults" section (your call — whichever is more discoverable for admins).
