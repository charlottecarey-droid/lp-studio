Replit Prompt — Full Email Template + Workflow Authoring
The shipped lifecycle notifications system (74665d7be) gave us the rails — notification_templates + notification_sends, dispatcher, in-app inbox, Resend send path, day 7/11/13 sweep — but the templates themselves are code-registered and the branded HTML shell is hardcoded in artifacts/api-server/src/lib/notifications.ts. Charlotte's ask: every email fully authorable from superadmin (subject + body + branded shell), with WYSIWYG and full-HTML modes, two scopes (LP Studio platform emails + tenant product emails), and let new templates + triggers + workflows be created without code.
This is meaningful expansion — roughly 2-3 weeks of work properly done. Phasing into three increments so something usable ships in the first few days, then progressively unlocks. Reuse heavily from the existing sales campaign editor and scheduler (sales-campaign-detail.tsx, CampaignVarInserter.tsx, sales_email_campaigns table) — both the rich editor component and the scheduler state machine are already battle-tested in production for tenant-side sales outreach. The lifecycle authoring system extends those patterns rather than rebuilding them.

Architectural anchor: reuse the campaign scheduler pattern
The sales_email_campaigns table already implements the right state machine for scheduled email delivery:

status enum: draft | scheduled | sending | sent | paused
scheduledAt timestamp column
Audience resolution via metadata + tenant-scoped query builder
Template attached via templateId foreign key
Send route at POST /campaigns/:id/send handles audience expansion + per-recipient delivery

Phase 3 of this plan extends that pattern (multi-step sequences, conditional branching, platform-scope) rather than building a parallel workflow engine. Phase 1 decisions should not accidentally diverge from this trajectory. Specifically: the same state machine values, the same scheduledAt column shape, and the same campaign-detail UI layout (audience pane + template editor + schedule controls) should appear in the new lifecycle authoring surface.

What's shipped vs what's missing
Shipped in v1 (74665d7be):

notification_templates table with seeded rows (welcome, trial day 7/11/13, expired, upgrade confirmation)
notification_sends log table
notificationDispatcher.ts with per-recipient×channel dedupe, claim/release-on-fail
notificationTemplates.ts code registry + cached DB accessor
In-app NotificationBell in header, inbox routes
SuperAdminNotifications tab — basic list view + patch subject/body
Daily sweep cron, in-app welcome on onboarding

Still hardcoded / missing:

Branded HTML shell in notifications.ts is a string literal — every email uses the same Dandy-green-on-cream header forever; superadmin can't edit it
Body HTML for seeded templates is in code; admin patch in v1 is a textarea, not a real editor
No WYSIWYG editor — only raw textarea
No way to create NEW templates from the UI (have to edit notificationTemplates.ts and deploy)
No way to create NEW triggers — trigger types are an enum baked into the dispatcher
No tenant-scope at all — every email is platform-scope (LP Studio → tenants); tenants can't edit the shell/templates for their own product emails (form notifications, outreach, microsite shares)
No multi-step workflows — every template is a single fire, no "if no response in 3 days, send follow-up" capability
Variable interpolation is per-template ad-hoc, no formal registry


Phasing

Variable inserter (reuse CampaignVarInserter)

Phase 3 (post-launch v1.2, ~5-7 days — DOWN from ~1-2 weeks because of campaign-scheduler reuse): Workflow composer + new template/trigger creation.

New tables notification_workflows + notification_workflow_steps modeled on the campaign state machine
Superadmin UI reuses the campaign-detail layout (audience pane + step list + schedule controls), swapped variable set and audience source
New step types: send_template (default), wait (delay N hours/days), branch (if/else on condition), wait_for_event ("if read_at is set on the prior step within 24h, fork")

Worker stays lazy-on-read (no cron) — same pattern as the trial expiry resolver and the daily sweep already in 74665d7be's server.ts

Each phase ships independently and is usable on its own.

No tenant-scope yet: all editing is platform-scope. Tenant editor + tenant product emails are Phase 2.

Preview iframe sandboxing: <iframe sandbox="allow-same-origin"> — no scripts execute, no top-frame navigation. Email previews are HTML strings from the backend; never trust them as live JS.

Schema additions:
sqlCREATE TABLE notification_workflows (
  id SERIAL PRIMARY KEY,
  scope TEXT NOT NULL CHECK (scope IN ('platform', 'tenant')),
  tenant_id INTEGER REFERENCES tenants(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  description TEXT,
  -- Same state machine as sales_email_campaigns.status
  status TEXT NOT NULL DEFAULT 'draft' CHECK (status IN ('draft', 'scheduled', 'sending', 'sent', 'paused')),
  trigger_type TEXT NOT NULL,  -- 'event', 'scheduled', 'audience_query'
  trigger_config JSONB NOT NULL DEFAULT '{}'::jsonb,
  audience_filter JSONB NOT NULL DEFAULT '{}'::jsonb,
  audience_provider TEXT NOT NULL CHECK (audience_provider IN ('platform_users', 'sales_crm')),
  -- For scheduled triggers; same column shape as sales_email_campaigns.scheduledAt
  scheduled_at TIMESTAMPTZ,
  active BOOLEAN NOT NULL DEFAULT true,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE notification_workflow_steps (
  id SERIAL PRIMARY KEY,
  workflow_id INTEGER NOT NULL REFERENCES notification_workflows(id) ON DELETE CASCADE,
  step_index INTEGER NOT NULL,  -- order within the workflow
  step_type TEXT NOT NULL CHECK (step_type IN ('send_template', 'wait', 'branch', 'wait_for_event')),
  -- For send_template: { template_key, channel_override? }
  -- For wait: { duration_hours }
  -- For branch: { condition: { var, op, value }, true_step_index, false_step_index }
  -- For wait_for_event: { event: 'read' | 'click', within_hours, on_event_step_index, on_timeout_step_index }
  step_config JSONB NOT NULL,
  UNIQUE (workflow_id, step_index)
);

CREATE TABLE notification_workflow_runs (
  id SERIAL PRIMARY KEY,
  workflow_id INTEGER NOT NULL REFERENCES notification_workflows(id),
  recipient_user_id INTEGER,
  recipient_tenant_id INTEGER,
  current_step_index INTEGER NOT NULL DEFAULT 0,
  status TEXT NOT NULL DEFAULT 'running' CHECK (status IN ('running', 'completed', 'failed', 'cancelled')),
  next_check_at TIMESTAMPTZ,  -- when the lazy-on-read scheduler should re-evaluate
  context JSONB NOT NULL DEFAULT '{}'::jsonb,
  started_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  completed_at TIMESTAMPTZ
);
UI: extend the campaign-detail layout for lifecycle workflows. The campaign editor is a three-pane shape — audience picker (left) + template editor (center) + schedule controls (right). Lifecycle workflow editor uses the same shape with one substitution: the template-editor pane becomes a step list with drag-to-reorder, and each step opens a sub-editor (template editor for send_template, duration picker for wait, condition builder for branch).
Audience provider abstraction. The existing campaign audience picker hardcodes queries against sales_contacts + sales_accounts. To reuse the UI layout for lifecycle workflows (where the audience is platform users + tenants), introduce a thin audienceProvider abstraction so the same picker UI can resolve either data source. Phase 3 work:
tsinterface AudienceProvider {
  key: "platform_users" | "sales_crm";
  filterSchema: AudienceFilterSchema;  // declarative filter UI shape
  resolveAudience(filter: JSONValue, scope: { tenantId?: number }): Promise<Recipient[]>;
}
platform_users resolves against tenants + users + trial state (LP Studio's own customers). sales_crm resolves against sales_contacts + sales_accounts (the tenant's prospects). Same UI, different data source.
Worker pattern: lazy-on-read, same as the trial expiry resolver in 74665d7be's server.ts. Every page load (or every dispatcher tick) iterates notification_workflow_runs WHERE next_check_at <= now() AND status = 'running', advances each one through its step machine, persists the next checkpoint. No cron job. Single source of truth for state is the database.
Open-ended template/trigger creation: the existing notification_templates table accepts arbitrary trigger_type + trigger_config already. Phase 3 just adds UI to create new rows from superadmin (button: "New template" → editor opens with blank slate). The trigger composer is a small visual form: pick trigger type (event / scheduled / audience query) → fill in config based on selection → save. No new schema needed; just UI on top of the existing column shape.
Migration of existing single-fire templates: each existing template becomes a trivial one-step workflow in the new system. The dispatcher's daily sweep continues to work; it just calls into the workflow runner instead of the single-template send path. Workflow runs with one send_template step are functionally identical to the v1 single-fire dispatcher.
